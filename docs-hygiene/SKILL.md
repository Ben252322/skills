# 文档卫生（docs-hygiene）

## 目的

防止项目文档腐烂。腐烂的根源不是疏于维护，而是文档里存放着与代码平行的真相
（字段表、页面清单、测试数……）。本 skill 提供目录约定、文档生命周期、机械门禁脚本，
以及在新项目落地的方法。

## 何时使用

- 设计或重组 `docs/` 目录结构
- 创建一篇设计文档并计划它的登记与状态流转
- 判断某篇文档该保留、改写还是删除（漂移、过时、一次性快照）
- 回答「设计文档开发完成后怎么处理」「什么时候归档」
- 为项目搭建文档引用可达性检查并挂进提交门禁

## 工作流

### 1. 建立或核对约定

读取 `references/maintenance-rules.md`：三态图例、权威源指认表、五条硬规则、归档三问。
目标项目尚无 `docs/README.md` 时，按该文件创建；已有时核对是否满足五条硬规则。

### 2. 按生命周期处置文档

读取 `references/lifecycle.md`，按四个时点处置：

| 时点 | 动作 |
| --- | --- |
| 创建 | 进 `design/`，状态「设计·待实施」，登记索引 |
| 需求提交 | 同一个 commit 改状态为「实施中/已实施」，文档留 `design/` |
| 被取代 | 替代设计合入的同一个 commit 删除旧文档 |
| 行动项关闭 | 执行型文档并入活文档后才删；未关闭的登记「待结项」 |

记住两个反直觉结论：设计文档**不需要主动归档**（`design/` 就是档案归宿，被取代才消失）；
「过了一段时间」不是归档理由，归档只跟事件走。

### 3. 落地机械门禁

将 `scripts/check-docs-links.js` 拷入目标项目 `scripts/`（按文件头注释调整配置区），
`package.json` 接线，并挂入既有 `test:verify` 提交门禁。完整步骤见
`references/adopt-in-new-project.md`（含 AGENTS.md 追加章节与发布 checklist 挂点）。

```json
"check:docs": "node scripts/check-docs-links.js",
"test:verify": "npm run lint && npm run check:docs && npm run test:unit && npm run test:integration"
```

### 4. 判断单篇文档去留（三问）

1. 未来 6 个月还会有人按它行动吗？
2. 它描述的东西有没有更靠近真相的源头（代码/测试/基础设施脚本）？
3. 它的错误描述会造成「浪费时间」还是「生产事故」？

三个都答不上来就删——git 即归档，删除无不可逆风险。

## 边界

- 本 skill 管**文档与规范**，不管代码质量（那属于 code review 范畴）。
- 不设定期文档 review；所有检查挂在既有事件（提交、发布）上。质疑此设计的论证见
  `maintenance-rules.md` 末节。
- 包装文档 ≠ 压缩文档：含未关闭行动项的文档，先并入活文档再删除原文件。
