# 设计文档生命周期

以一次需求为例，设计文档的四个时点。每一步都绑定在一个**已有事件**上（提交代码 / 发布），不需要额外的「定期文档 review」。

| 时点 | 动作 | 触发事件 |
| --- | --- | --- |
| 创建 | 放入 `design/`，状态「设计·待实施」，登记索引 | 设计定稿的 commit |
| 开发完成、提交代码 | **同一个 commit** 把状态改为「实施中 / 已实施」；含落地批次表的标注完成批次与 commit hash。文档**留在 `design/`** | 需求代码提交 |
| 被取代或推翻 | 新设计合入的**同一个 commit** `git rm` 旧文档 | 替代设计提交 |
| 行动项全部关闭（仅执行型文档） | 发布待办、迁移清单、审计报告这类含未关闭行动项的文档登记为「待结项」；行动项关闭并并入对应活文档后才删除 | 每次发布时的「文档结项」检查项 |

## 三个常见问题的答案

**Q：需求开发完了，提交的时候设计文档怎么处理？**
同一个 commit 更新状态头与索引登记；文档留在 `design/`。设计文档提交后的正常归宿就是长期躺在 `design/` 当档案——它的价值是「为什么这么做、边界在哪、推翻了什么」，代码里读不出来。

**Q：过了一段时间可以归档了，什么时候归档？**
没有"过了一段时间"这个触发器。设计文档只有两个消失时点：被新设计取代（写新设计时必然看到旧的，事件会替你想起）、行动项关闭的执行型文档（发布 checklist 的「文档结项」项替你想起）。`design/` 是档案归宿，不要求归档清空。

**Q：什么文档会在提交时变成「待结项」？**
含未关闭行动项的执行型文档：发布待办清单、迁移清单、审计报告、验收记录。**永远不要在还有未关闭行动项时"压缩"这类文档**——压缩 = 静默丢失任务。正确做法：行动项并入对应活文档（如发布 checklist），确认无遗漏后才删除原文档。

## 反模式（真实教训）

- `2026-05-30-bootstrap-auth.md`（1612 行）：TDD 步骤 + 完整测试代码 + git 提交命令，与 git 历史 100% 重复，其「已知限制」早被实现打脸——写完即腐烂的典型。
- `2026-08-09-init-user-roles.md`：集合当天就删了，但 runbook 步骤区仍完整可执行——「标题写已废弃」拦不住误操作。
- 一次性交接报告：测试数、部署清单、阻塞项全是时点快照，无一当前有效。
