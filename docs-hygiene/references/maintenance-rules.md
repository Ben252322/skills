# 文档卫生标准（维护规则全集）

> 来源：keshiqing-miniapp 仓库 2026-10-16/17 文档重组实践，经 reviewer subagent 评审修订。
> 本文件是标准的完整版；SKILL.md 只保留触发与流程。

## 核心命题

**文档腐烂不是因为没人维护，而是因为文档里放着一份和代码平行的真相。** 平行真相必然漂移：代码天天变，文档写下的那一刻就开始过期。因此所有规则都指向两个动作：

1. 让可漂移的内容**不存在于**文档中（只写决策，不镜像事实）；
2. 把"发现腐烂"**机械化**（引用可达性检查），而不是依赖人或定时任务。

业务契约文档定义期望规则，由代码与测试实现和验证，不属于实现事实的镜像。项目需明确登记契约根文档；契约根之间可互引、可被其他文档引用，但**不得直接深入引用 `docs/design`、`docs/runbooks` 内的非根文档**——细节引用经 `docs/README.md` 索引中转（由 `CONTRACT_ROOTS` 机械检查保证方向）。契约规则与实现冲突时，先确认需求是否变更，再决定修规范或实现。

## 目录约定

```
docs/
├── README.md            # 索引：状态图例、权威源指认、维护约定（硬规则）
├── testing-strategy.md  # 活文档示例
├── design/              # 设计决策记录（YYYY-MM-DD-*.md）
└── runbooks/            # 运维手册（只留环境生命周期内会再次执行的操作）
```

根目录另可有发布类活文档（如 RELEASE_CHECKLIST.md），但同类文档只允许一个位置。

## 状态图例

| 状态 | 含义 | 更新时机 |
| --- | --- | --- |
| 活文档 | 约定、门禁、发布操作 | 随代码变更同批提交 |
| 设计·已实施 | 不变量、决策与理由的权威来源 | 设计被实质推翻时修订 |
| 设计·实施中 | 有未落地批次 | 每批落地时更新状态 |
| 待结项 | 含未关闭行动项 | 行动项关闭、并入活文档后删除 |
| 待核验 | 历史文档，完成状态无法从源码/测试/交付记录确认 | 核验后转为确定状态，或按去留判据删除；不得把未勾选步骤当作当前待办，也不得猜测为已完成 |

## 权威源指认（truth table）

| 想了解什么 | 去哪看 |
| --- | --- |
| 期望字段、接口契约、业务规则 | 项目登记的业务契约根文档；实现与覆盖由代码和测试证明 |
| 当前实现字段、接口与行为 | 源码与测试 |
| 集合/索引清单、权限、环境变量、部署事故记录 | 发布 checklist / 基础设施脚本 |
| 页面清单与路由 | app.json / 路由配置 |
| 历史实施过程 | git 历史（删除的文档均可按 commit 取回） |

文档记录决策、约束和期望契约；不要复制可从代码、测试或配置机械取得的当前实现事实。

## 硬规则

1. **分开契约与实现。** 业务契约根定义期望行为；文档不复制可从代码/git 导出的实现清单、测试数量或环境快照。
2. **新文档必须登记。** 文档进 `design/` / `runbooks/` 时必须登记进 `docs/README.md` 索引，文件头含 `**日期：**` 与 `**状态：**`，文件名以 `YYYY-MM-DD-` 开头。
3. **引用必须可达。** 代码注释与文档中引用 `docs/**` 的路径必须指向真实文件；死链在提交门禁失败（`check-docs-links.js`）。
4. **状态随代码同批更新。** 「实施中→已实施」「待结项→已并入」与对应代码变更同一次提交；不允许只改代码不改状态。
5. **runbook 只留会再次执行的。** 一次性初始化步骤（建表/建索引/跑迁移）完成后即删除；清单类权威源是发布 checklist。
6. **契约根引用方向。** 索引登记契约根；根文档可互引、可被其他文档引用，但不得直接深入引用 `docs/` 内非根文档（细节经索引中转）；`CONTRACT_ROOTS` 机械检查保证该方向。

## 去留判据

按生命周期和内容价值决定去留：

1. 已实施设计保留其决策与理由，直到被新设计实质替代；不按年龄归档或删除。
2. 有未关闭行动项的执行文档标为待结项；行动全部并入活文档后删除。
3. 过期快照、重复说明和可机械取得的实现事实，在确认无未结事项后删除。

删除文档时先更新所有引用；git 历史可追溯，但不能替代仍需使用的决策记录。

## 约束规范为什么单独不够（给质疑者的回答）

- 约束的形状是"改 X 时同步改 Y"，只对**正在发生的变化**生效；从写完就没人再打开的文档，没有任何变更会触发更新它。
- 违反文档约束**当时没有报错**——"标题写已废弃、步骤却完整可执行"的 runbook 照样骗到运维。
- 因此：可机械执行的规则才进硬门禁（引用可达），其余规则靠事件绑定（提交 / 发布）执行，**不设"定期文档 review"**——没有所有者的定时任务在个人项目里必然消亡。
